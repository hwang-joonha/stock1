# 추정 모델링 프레임워크

투자심사용 재무 추정 모델을 세우는 규약. 종목이 바뀌어도 이 규약은 바뀌지 않는다.

관련 문서
- [`html_template_spec.md`](html_template_spec.md) — 노드 스키마·수식 문법·엔진 계약
- [`ic_memo_framework.md`](ic_memo_framework.md) — 투자심사 판단 레이어
- [`excel_spec.md`](excel_spec.md) — Excel 산출 규격

---

## 1. 두 가지 입력 경로

| 경로 | 상황 | 첫 작업 |
|---|---|---|
| **Case A** | 기존 엑셀 모델이 있다 | 로직 역추출 → 노드 트리로 재구성 |
| **Case B** | 모델이 없다 | 공시·리서치에서 로직 신규 설계 |

삼성전기는 Case B다.

---

## 2. 작업 순서

```
① 리서치        공시 원문에서 실적 시계열 확정
② 설계          methodology.md — Q×P 분해 트리, 추정 로직, 가정변수
③ 빌드          data.js — 설계를 노드로 옮김
④ 검증          validate_model.py — 전 게이트 통과
⑤ 산출          model.html → ir.json → model.xlsx
```

**순서를 건너뛰지 않는다.** ①이 끝나기 전에 ③으로 가면 근사치가 모델에 굳는다.
Tesla 작업에서 실제로 그렇게 됐고, 전 연도를 다시 확정해야 했다.

## 3. 실적 데이터 확정 원칙

### 3.1 확정 vs 검증대상

라인아이템마다 상태를 명시한다.

| 표시 | 뜻 | 다음 단계로 넘어가도 되는가 |
|---|---|---|
| `[확정]` | 공시 원문(사업보고서·분기보고서·10-K·8-K)의 손익계산서에 그 숫자가 그대로 있다 | 예 |
| `[검증대상]` | 합계에서 역산했거나 기사에서 가져왔다 | **아니오** |

`[검증대상]`이 하나라도 남아 있으면 Excel 단계로 넘어가지 않는다.

### 3.2 reconcile 검증

세그먼트 합계가 총계와 **정확히** 일치해야 한다. "거의 맞다"는 통과가 아니다.
전 연도에 대해 코드로 확인한다. `historicals.json`에 확정값을 적어두면
`validate_model.py`의 G1이 매번 대사한다.

### 3.3 주식수·회계기준 변동

무상증자·액면분할·회계기준 변경이 있으면 시계열이 끊긴다.
어느 기준으로 통일했는지 `desc`에 반드시 적는다. 혼용은 금지.

## 4. Q×P 재귀 분해

### 4.1 분해 원칙

매출을 물량(Q) × 단가(P)로 쪼갠다. **트렌드가 식별될 때까지만** 쪼갠다.

분해를 멈추는 기준:
- 더 쪼개면 데이터가 없다
- 더 쪼개도 추세가 더 선명해지지 않는다
- 쪼갠 단위마다 별도 가정을 세울 근거가 없다

과분해는 정밀해 보이지만 가정만 늘린다. 가정이 늘면 틀릴 자리가 늘어난다.

### 4.2 추정 방식 3분류

각 추정단위가 무엇에 묶여 있는지 먼저 정한다. 이걸 정하지 않으면
생산능력이 남는데 물량을 capacity로 추정하는 실수가 난다.

| 분류 | 상한을 정하는 것 | 접근 | 전형적 대상 |
|---|---|---|---|
| **수요 바인딩** | 시장 수요 | top-down (시장규모 × 점유율) | 성숙 제품, 전방산업이 정체된 부문 |
| **공급 바인딩** | 생산능력 | bottom-up (capacity × 가동률) | 증설 중인 신규 라인, 물량이 밀리는 부문 |
| **외생** | 정책·계약 | 시나리오 step | 규제 크레딧, 일회성 계약 |

외생 항목은 Q×P로 쪼개지 않는다. 억지로 쪼개면 없는 구조를 지어내는 것이다.

수요 바인딩 부문에도 `production_capacity`를 **상한 체크**로 둔다.
수요 추정 합계가 capacity를 넘으면 모델이 잘못된 것이다.

### 4.3 객관 / 주관 구분

모든 리프 노드에 태그를 단다. `desc`의 맨 앞에 온다.

| 태그 | 뜻 | 시나리오 분기 대상 |
|---|---|---|
| `[객관]` | 공시·계약·물리적 제약에서 나온 값 | 아니오 |
| `[주관]` | 분석자의 판단이 들어간 값 | **예** |
| `[외생]` | 정책·환경 변수 | 예 |
| `[계산]` | 다른 노드에서 유도된 값 | 아니오 |

`[주관]`은 상한/하한을 먼저 잡고 시나리오로 분리한다.
Bull/Base/Bear는 `[주관]` 노드만 움직여서 만든다 — `[객관]`을 흔들면
시나리오가 아니라 다른 모델이 된다.

`validate_model.py`의 G10이 태그 누락을 잡는다.

## 5. 노드 설계 규칙

### 5.1 이름

노드 id는 영문 소문자·언더스코어. 화면에 나오지 않으므로 짧게, 다만
수식에서 읽혀야 하므로 뜻이 통하게. `del_3y`(인도량)처럼 계열을 접두어로.

### 5.2 공유 드라이버

같은 값을 두 곳에서 따로 추정하지 않는다. 한 번 추정하고 참조한다.

전형적 공유 드라이버:

| 드라이버 | 매출 측 | 비용 측 |
|---|---|---|
| 출하량 | 제품 매출 | 변동원가, 물류비 |
| 가동률 | 생산 물량 | 고정비 배부, 단위원가 |
| CAPEX | (없음) | 감가상각비 |
| 누적 설치대수 | 서비스 매출 | 서비스망 운영비 |

매출 설계 단계에서 **비용과 공유할 드라이버를 미리 식별해 둔다**.
나중에 비용 트리를 붙일 때 배선만 하면 되도록.

### 5.3 단방향 흐름

드라이버 → 파생값 순서가 한 방향이어야 한다.
`인도량 → ASP 믹스 → 서비스 누적`처럼. 양방향으로 얽히면 순환참조가 된다.

예외는 `PREV()`로 표현되는 시차 참조뿐이다. 이건 순환이 아니다 —
전년 값을 읽는 것이므로 시간 방향으로는 여전히 단방향이다.

### 5.4 누적·롤포워드

자기 자신의 전년 값을 참조하는 계정은 `PREV(자기id)`로 쓴다.

```js
installed_base: {
  type:'computed',
  formula:'PREV(installed_base) + additions',
}
```

감가상각 스케줄, 순차입금 롤포워드, 누적 설치대수가 전부 이 형태다.
장치산업 모델에서는 피할 수 없다.

## 6. 시간축

- 실적 연도를 앞에, 추정 연도를 뒤에 둔다.
- `HIST_N`이 그 경계다. 실적 구간은 시뮬레이터에서 잠긴다.
- 실적 4~5개년 + 추정 5개년이 기본. 추세를 읽을 만큼은 있어야 하고,
  너무 길면 앞쪽 실적이 현재와 무관해진다.

## 7. 검증 게이트

`validate_model.py`가 돌린다. 전부 통과해야 다음 단계로 간다.

| 게이트 | 검사 |
|---|---|
| G1 | 실적 구간 값이 공시 확정값과 일치 |
| G2 | 합계형 노드 = 자식 합 |
| G3 | 노드 평가 오류·순환참조 0 |
| G4 | INPUT_KEYS ↔ DEFAULTS_S 일치 |
| G5 | 전 노드 값 배열 길이 = YRS 길이 |
| G6 | 미사용 가정변수 0 |
| G7 | HTML 산출값 ↔ Excel 수식 평가값 대사 |
| G8 | JS 문법 · 고아 노드 0 |
| G9 | Tesla 골든 샘플 회귀 (엔진 수정 시) |
| G10 | 입력 노드 근거 태그 |

**"거의 통과"는 통과가 아니다.** 특히 G1·G2의 오차 허용치는 0이다.

---

## 8. 하지 말 것

- 숫자를 추정으로 때우고 넘어가기 — `[검증대상]`으로 표시하고 확정하고 오기
- 근거 없이 노드 쪼개기 — 정밀해 보이지만 가정만 늘어난다
- 같은 드라이버를 두 곳에서 따로 추정하기 — 반드시 갈라진다
- `[객관]` 노드를 시나리오로 흔들기 — 그건 다른 모델이다
- 게이트 실패를 남겨두고 다음 단계로 가기
